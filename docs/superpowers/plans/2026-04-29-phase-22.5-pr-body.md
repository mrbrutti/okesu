## Summary

Phase 22.5 of the threatcaddy-borrows plan
(`docs/superpowers/specs/2026-04-29-threatcaddy-borrows-phasing-design.md`).

- New IOC catalog kinds `yara_rule` and `sigma_rule` (parser + loader
  integration in `controlplane/ioc/catalog/`). Header metadata is
  auto-extracted so the YAML wrapper stays minimal; explicit fields
  always win over parsed defaults.
- New `name TEXT` and `tags TEXT` columns on `iocs` (migration 039),
  threaded through `IOCUpsert` and `IOCRecord`.
- New endpoint `GET /api/catalog/yara-rules.yar?tag=<tag>` returns a
  concatenated YARA rule bundle the `binary-analyzer` agent can pipe
  into the system `yara` CLI.
- `binary-analyzer` agent prompt extended with a "Catalog YARA scan"
  methodology section: fetch bundle → temp file → `yara -r` → emit
  `ioc_observation` findings on match.
- Worked example catalog entries for both YARA and Sigma kinds.
- Sigma is **storage-only** in v1; per-host log-adapter execution is
  deferred.

YARA parser handles the common rule-header forms found in third-party
corpora: optional `private` / `global` modifiers, optional tag list,
optional `meta.severity` line.

Build matrix unchanged: every binary still ships with
`CGO_ENABLED=0`. The YARA execution path is via the agent's shell
tool, not a Go binding.

## Open follow-ups

- Sigma execution via a per-host log-adapter — out of scope for v1.
  Deferred until a real customer needs it; storage-only is enough for
  catalog inventory and sharing today.
- Tag-indexed lookup on `iocs` — for v1 the YARA bundle endpoint
  filters tags in Go after fetching all `yara_rule` rows. With <1k
  curated rules this is fine; revisit when the catalog grows past
  that.
- Sigma parser hardens: a `tags:` value that's a YAML map (operator
  typo) currently bails out and drops all extracted metadata, not
  just tags. Worth catching with a `yaml.Node` decode pass.
- Federation propagation of `name`/`tags` columns — the existing
  IOC federation flow (Phase 22.1) propagates the row as a whole, so
  no extra wiring needed, but lab-smoke should confirm a parent CP
  pushes a yara_rule with non-empty name/tags to a child correctly.

# Okesu

Autonomous AI agents for security operations — running, supervised,
and federated across a fleet via a Go control plane.

Okesu ships as a single binary with several subcommands:

| Command | What it does |
|---|---|
| `okesu claude` / `okesu codex` / `okesu auto` | One-shot agent run with the chosen provider. |
| `okesu daemon --agent <name>` | Long-running daimon that ticks on a schedule, emits findings, hot-reloads from CP config. |
| `okesu jobs --cp-url …` | Pull-mode jobs runtime — host worker the orchestrator dispatches agent runs through. |
| `okesu node` | Reverse-mTLS tunnel client for low-latency dispatch on hosts that can reach the CP. |
| `okesu enroll --bootstrap …` | First-boot S3-transport enrollment — used by self-registering install packages. |

The control plane (`okesu-cp serve`) is a separate Go web app +
React UI that aggregates events, drives orchestrations, manages the
node fleet, and is itself federation-aware (parent CPs proxy
read/write across child CPs).

## Highlights

- **Run the same agent locally, on any node, or via the orchestrator.**
  Identical JSONL transcript regardless of how you launched it.
- **Multi-provider** — Anthropic and OpenAI, with `auto` inferring
  from the agent file's `provider:` frontmatter.
- **Daemon mode** — agents tick on a schedule (cron or interval),
  carry persistent state across ticks, and report through one of two
  mgmt-plane transports (HTTPS pull-mode or S3 dead-drop).
- **Orchestrations** — chain agents, fan out across hosts, gate on
  operator approval, and **mutate finding state via the engine-applied
  action protocol** so T1 chains *resolve* findings instead of
  emitting briefs nobody reads.
  See [docs/orchestrations.md](docs/orchestrations.md) and the
  T1/T2 library at [examples/orchestrations/](examples/orchestrations/).
- **Federation** — parent ↔ child CPs proxy events, runs, and
  deploys. The UI surfaces every result with a per-CP source chip.
- **Multi-OS deploy** — single ServiceManager interface targets
  systemd / launchd / rc.d / SMF. The same install path covers
  Linux, macOS, FreeBSD, OpenBSD, illumos.
- **S3 dead-drop transport** — for nodes that can't reach the CP
  but can reach object storage (NAT, air-gap, DMZ). Fleet packages
  generated by the CP self-register N machines via a shared bucket.
  See [docs/s3-transport.md](docs/s3-transport.md).

## Quick start (local lab)

Prerequisites:

- Go 1.23+
- Node + npm (for the UI build)
- Docker / nerdctl / Lima with nerdctl (for the lab containers)
- An `~/.config/.env` with `ANTHROPIC_API_KEY=…`

```bash
# Build host + linux daemon, build UI, embed it into the CP.
make daemon-host cp
( cd web && npm install && npm run build )

# Bring up the federated lab — three CPs (global / east / west) and
# 30 sshtarget containers split across east + west.
./test/stack/start-federated.sh

# Open https://localhost:7443 (admin@local / okesu-demo).
```

The lab has the T1/T2 orchestration library pre-installed on east +
west. Findings flow up via federation; auto-triage classifies and
mutates them; the dashboard's **Automation** + **Pending approvals**
cards show the result. Cmd-K surfaces pending gates and orchestration
search.

To stop:

```bash
./test/stack/stop-federated.sh
```

## CLI cheatsheet

```bash
# One-shot agent run
okesu claude "review ./src for auth bypasses"
okesu claude --agent investigator "look at finding #245"

# Daemon mode (HTTPS pull transport)
okesu daemon --agent edr

# Pull-mode jobs runtime — host worker the orchestrator dispatches through
okesu jobs --cp-url https://cp:8444 --cert-dir /etc/okesu/node-certs --name web-01

# S3 dead-drop enrollment (consumed by an install package)
sudo /usr/local/bin/okesu enroll --bootstrap /etc/okesu/bootstrap.json

# Reverse-mTLS tunnel for hosts that CAN reach the CP
okesu node --cp-url https://cp:8444 --cert-dir /etc/okesu/node-certs --name web-01
```

## Adding an agent

Drop a `.md` file under `~/.claude/agents/` (or any path passed to
`--agent-files-dir` on the CP). Frontmatter declares the runtime
shape; the body is the system prompt:

```yaml
---
name: my-watchdog
description: Watch for foo. Emit findings when bar.
provider: claude
model: claude-mythos-preview
tools: [bash, read_file]
maxTurns: 30
interval: 60s
permissionMode: bypassPermissions
---

You are …
```

See `examples/agents/` for production-grade examples (edr,
instance-integrity, instance-threat, sre-health, oci-posture).

## Adding an orchestration

YAML; one file per orchestration. See
[docs/orchestrations.md](docs/orchestrations.md) for the full
reference and [examples/orchestrations/README.md](examples/orchestrations/README.md)
for the conventions used across the T1/T2 library.

The action protocol — how a step asks the engine to mutate finding
state on its behalf — is the unlock that makes T1 actually
resolve issues:

```yaml
- id: classify
  agent: investigator
  actions:                              # default deny — engine validates
    - update_finding_status
    - set_finding_severity_override
    - add_finding_tag
    - link_run_to_finding
  prompt: |
    Classify finding #{{trigger.finding_id}}.
    Emit an orchestration_result with attributes:
      verdict, reasoning, actions (array of {kind, finding_id, …})
```

The agent's `actions[]` array is validated against the step's
allowlist; rejections are logged but don't abort the run. Every
applied action writes to `finding_edits` so the finding-detail
**History** panel shows "auto-resolved by run #N — 12m ago".
